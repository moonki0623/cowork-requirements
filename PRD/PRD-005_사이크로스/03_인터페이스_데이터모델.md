# 인터페이스 및 데이터 모델 스펙 (v3)

> 02 TO-BE 아키텍처의 구현 계약 상세. ❓ 표기는 04 Open Questions 참조.

## 1. 소스 데이터 명세

### 1-1. Sycros 폴링 테이블: `event_text_hist_YYYYMMDD` ✅

- 일별 테이블, 자정 생성 ✅. 컬럼: event_id, host_name, host_alias, ip_address, event_name, class_name, instance_name, resource_name, parent_name, create_date, accept_date, state, value, unit, message, event_source, exception
- `event_id`: 18자리 zero-padded 고정폭 = YYYYMMDD(8) + HHMMSS(6, 적재 시각) + 초당 시퀀스(4, 매초 리셋). 사전순 비교 안전 ✅
- `state` ✅: 1 normal / 2 warning / 3 critical / 4 fatal. 신규 라우팅은 critical 이상만 처리 ✅ (A32)
- 스레드 시간 기준: **create_date** ✅ (B6 확정) — 판정은 이벤트 create_date끼리 비교(서버 시계 혼용 금지). NMS 계열의 create/accept 역전은 소스 간 문제로, 호스트 단위 스레드 키에서는 영향 없음
- `event_name`: Control-M 식별은 event_name='CTRLM' (exclude 필터 축)
- `exception`: **무시** ✅ (A31)

### 1-2. 정규화 이벤트 모델 (AlarmEvent)

```go
type AlarmEvent struct {
    Source     string    // "sycros" | "tmax"
    EventID    string    // sycros: event_id / tmax: 플러그인 채번(§2)
    RoutingKey string    // sycros: lower(host_name) / tmax: 업무코드 대문자
    Severity   string    // normal|warning|critical|fatal (tmax: 항상 critical)
    Title      string
    Body       string
    HostAlias  string
    EventName  string
    OccurredAt time.Time // sycros: create_date / tmax: occurred_at 또는 수신 시각
    Raw        map[string]any
}
```

키 비교는 대소문자 무시. 표기 관례: sycros 호스트 소문자, tmax 업무코드 대문자.

### 업무코드(라우팅 키) 추출 규칙 ✅ (A30)

```go
lines := strings.Split(body, "\n")
serviceCode := strings.ToUpper(lines[1][:2])   // "lnhb0003u0..." → "LN"
```

- **body 2번째 라인의 첫 2글자를 대문자 치환** = 업무코드
- 예외(2번째 라인 부재, 2글자 미만, 영문 아님): unmatched 채널 발송 + 원문 로그
- ⚠ 이 규칙은 "2번째 라인이 배치잡코드로 시작"하는 포맷 유지에 의존 — Tmax 발신측과 해당 라인 불변 합의 필요 (D4)
- event_id: 원천에 없음 ✅ → 플러그인 채번 `TMX-{수신시각14자리}-{시퀀스}`
- 검증은 봉투만: schema_version(=1), body 비공백. title 누락 시 `[Tmax] {업무코드} 알림`, occurred_at 누락 시 수신 시각
- 응답: 202 {routed_channels: n} / 400(원문 로그 보존) / 401

## 3. 매핑 데이터 모델 (KV `mapping:v1`)

```json
{
  "version": 12,
  "updated_at": "2026-07-08T10:00:00+09:00",
  "updated_by": "kimdongho",
  "channels": {
    "it_div": {
      "channel_id": "abc123", "display": "IT부문", "priority": "urgent",
      "exclude": [{"field": "event_name", "keywords": ["CTRLM"]}],
      "jira": {"enabled": true, "project_key": "ITOPS", "issue_type": "장애", "labels": ["sycros"]}
    },
    "pension_alert": {"channel_id": "def456", "display": "퇴직연금알림"},
    "unmatched":     {"channel_id": "xyz789", "display": "알람-미매핑", "role": "fallback"},
    "audit":         {"channel_id": "aud001", "display": "알람-관리로그", "role": "audit"}
  },
  "rules": [
    {"source": "sycros", "key": "pmapiap01", "targets": ["it_div"]},
    {"source": "sycros", "key": "pinfodb01", "targets": ["it_div", "info_ops"]},
    {"source": "tmax",   "key": "RK",        "targets": ["pension_alert", "it_div"]}
  ],
  "settings": {
    "severity_min": "critical",
    "thread_window_sec": 120,
    "thread_max_age_sec": 1800,
    "thread_max_replies": 200,
    "dispatch_concurrency": 16
  }
}
```

- 채널 실체는 channels 한 곳에만, rules는 이름 참조
- 저장 시 version 비교(동시 편집 충돌 시 409 → UI 재로드)
- jira의 project_key/issue_type 필드는 N8(endpoint 범용형) 채택 시 사용, 고정형이면 enabled만

### KV 키 레이아웃

| 키 | 용도 | TTL |
|---|---|---|
| `mapping:v1` | 매핑 blob | — |
| `processed_channel_{event_id}` | 기존 row 선점 (계승) | 300s |
| `integration:jira` | Jira endpoint URL + PAT (관리화면 입력, **export 제외**) | — |
| `thread:{channel_id}:{source}:{key}` | 스레드 루트 post_id + 마지막 이벤트 시각 + jira_key | 캡+α |
| `channel_last_processed_position` | 폴링 위치 (기존) | — |

## 5. 메시지 렌더링 ✅ (A21, B4 확정)

발송 대상: critical(3)·fatal(4)만. warning 이하와 회복 이벤트는 어디에도 표시하지 않음.

### 루트 post (새 인시던트 = 해당 키의 열린 스레드 없음)

```
**[ 사이크로스 알림 ]** 🔴 CRITICAL
**호스트**: dlpap02 [개발_lpgo_dlpap02]
**발생일시**: 2026-07-08 10:04:11
─────────────────────────
[개발_lpgo_dlpap02] Memory Usage 83.51%로 임계치 초과되었습니다
```

Tmax 루트: 헤더 `**[ Tmax 알림 ]** 🔴 CRITICAL`, 호스트 라인 대신 `**업무**: RK (lnhb0003u0)`.

### 스레드 reply (120초 윈도우 내 같은 키의 후속 알람 — 루트 포맷에서 헤더 라인만 제거)

```
⛔ FATAL
**호스트**: dlpap02 [개발_lpgo_dlpap02]
**발생일시**: 2026-07-08 10:06:12
─────────────────────────
[개발_lpgo_dlpap02] Memory Usage 95.40%로 임계치 초과되었습니다
```

- 뱃지: 🔴 CRITICAL / ⛔ FATAL (발송 대상이 이 둘뿐)
- Jira 생성 시 스레드 reply 1건: `🎫 Jira 티켓 생성: ITOPS-1234 <링크>`

## 6. Jira 연동 — ScriptRunner 커스텀 endpoint ✅ (A29)

Jira 측에 ScriptRunner custom endpoint 신설(자체 작성, 기존 taskList 예제와 동일 방식). 인증은 보안 협의 후 발급될 API 계정 PAT. 플러그인 → endpoint 계약(안):

```
POST https://projects.miraeassetsecurities.com/rest/scriptrunner/latest/custom/createAlarmIssue
Header: Authorization: Bearer {PAT}   ← API 계정 PAT (보안 협의 후 발급)
{
  "summary": "[dlpap02] Memory Usage fatal — 사이크로스 알림",
  "description": "본문 + 발생시각 + MM 스레드 permalink",
  "project_key": "ITOPS", "issue_type": "장애",
  "labels": ["sycros", "dlpap02"]
}
→ 200 { "issue_key": "ITOPS-1234", "url": "https://..." }
```

- 트리거: 스레드 루트 생성 직후 비동기, 재시도 1회, 실패 시 감사 채널 알림 (알람 발송과 완전 격리)
- 티켓 키를 thread KV에 저장 (Phase 2 대비)
- endpoint URL·PAT는 관리화면 설정 탭에서 입력 ✅ (N9) — `integration:jira` KV에 매핑과 분리 저장, export/import 제외, 화면에는 마지막 4자리만 표시
- project_key·issue_type은 파라미터 유지(범용형) — endpoint를 고정형으로 만들 경우 플러그인이 보낸 두 필드를 무시해도 무방
- MM→Jira 방화벽: 확인 완료(열려 있음) ✅ (N10)
