## 1. 문제 정의

현행 알람 채널은 심각도(state) 단위로만 분류되어, 알람을 봐야 할 조직(팀/본부)이 자기 관련 알람만 골라 받을 수 없다. 업무 단위 재분류는 200개+ 업무의 매핑 사전작업이 필요해 수개월이 소요되므로, **조직 단위 채널 라우팅**을 최소 리소스로 빠르게 구축한다(단기 80점 → 점진 발전). 알람 소스도 Sycros 단일에서 Tmax 배치/서비스 알람까지 2종으로 확장되며, 동일 장애의 연속 알람이 채널을 도배해 알람 피로 → 뮤트 → 채널 무용화로 이어지는 문제를 스레드 묶음으로 해소한다. 본 프로젝트는 Slack + 차세대 모니터링 전환 전 프로토타입으로, 여기서 축적한 매핑 데이터와 운영 방식은 전환 시 재사용한다.

## 2. 목표

1. Sycros(hostname)·Tmax(업무코드) 알람을 **조직 채널로 M:N 라우팅** — 미매핑 유실 0건 (전량 fallback 채널 수용)
2. 동일 호스트 연속 알람의 채널 post 수를 스레드 묶음으로 대폭 축소 (폭풍 시 루트 1건 + reply)
3. 매핑 등록·수정을 **관리 웹뷰에서 셀프 처리** — 개발자 개입·플러그인 재시작 없이
4. IT부문 채널 인시던트를 **Jira 티켓으로 자동 기록** (스레드당 1건, 성공률 99%+)
5. 기존 기능(DM·state 라우팅) 무영향 — 회귀 0건

## 3. 비목표 (Non-Goals)

- **DM 파이프라인 변경 없음** — tb_kko_tran 폴링~DM 발송 경로는 코드·동작 동결
- **state 기반 채널 라우팅 대체 없음** — 영구 공존, 컷오버·정리 계획 없음
- **자정 롤오버 동작 수정 없음** — 현행 수용(알려진 제약으로 문서화)
- **파이프라인 간 이중발송 가드 없음** — state 채널과 매핑 채널은 별도 채널로 분리 운영(운영 규칙). 겹침 등록 시 이중 발송은 문서화된 동작
- warning 이하·회복 알람 표시 없음 / 팀별 셀프서비스 권한·Jira 코멘트 미러링·자동 종결은 Phase 2

## 4. 사용자 스토리

- 현업 팀원으로서, 우리 팀 서버/업무의 심각 알람만 팀 채널에서 받아 즉시 대응하고 싶다
- IT부문 운영자로서, 연속 장애 알람이 스레드 하나로 묶여 채널이 읽을 수 있는 상태로 유지되길 원한다
- 관리자(영업정보팀)로서, 서버 이관·조직 변경 시 웹 화면에서 매핑을 직접 고치고 dry-run으로 즉시 검증하고 싶다
- IT부문 운영자로서, 인시던트가 Jira 티켓으로 자동 기록되어 사후 추적·통계가 가능하길 원한다
- 관리자로서, 어떤 알람이 어디에도 매핑 안 됐는지 fallback 채널에서 확인하고 매핑을 보강하고 싶다

## 5. 기능 요구사항 (P0 = Phase 1 필수)

### FR-1. Sycros 폴링 소스 (기존 개선) — P0
event_text_hist_YYYYMMDD 폴링(기존 로직 계승)에서 state 3(critical)·4(fatal) 이벤트를 신규 라우팅 파이프라인에 공급한다.
- [ ] state 1·2 이벤트는 신규 파이프라인에서 발송·스레드 부착 모두 하지 않는다
- [ ] 목록+데이터 조회를 단일 쿼리로 개선한다 (N+1 제거)
- [ ] 기존 state 라우팅·DM 발송 경로의 동작은 변하지 않는다 (회귀 테스트)
- [ ] event_id 위치 비교는 현행 문자열 비교 유지 (18자리 zero-padded 확인됨)

### FR-2. Tmax 웹훅 수신 (신규) — P0
`POST /plugins/dmove-sycros/api/v1/ingest/tmax`, 토큰 헤더 인증, 봉투(schema_version, body)만 엄격 검증.
- [ ] 업무코드 = body 2번째 라인 첫 2글자의 대문자 치환 (lnhb0003u0 → LN)
- [ ] 파싱 실패(라인 부재·2글자 미만) 시 fallback 채널 발송 + 원문 로그
- [ ] event_id는 플러그인이 채번 (TMX-{수신시각}-{시퀀스})
- [ ] 전건 severity=critical 취급, 토큰 불일치 시 401 + 로그

### FR-3. 매핑 라우팅 (신규 핵심) — P0
`(source, key) → [채널...]` M:N. KV `mapping:v1` 단일 JSON, 메모리 캐시 TTL 30~60초.
- [ ] 동일 키 → 복수 채널, 복수 키 → 동일 채널 모두 동작 (병렬 발송, 개별 실패 격리)
- [ ] 키 비교 대소문자 무시. 채널 실체(channel_id)는 channels 정의에만 존재, rule은 이름 참조
- [ ] 매핑 변경이 플러그인/폴링 재시작을 유발하지 않는다
- [ ] 채널별 exclude 필터: 필드 지정(host_name/host_alias/message/event_name) contains, 초기값 빈 상태

### FR-4. 미매핑 fallback — P0
- [ ] 매핑에 없는 key의 알람은 전량 #알람-미매핑 채널로 발송되고 유실되지 않는다
- [ ] 발송·미매핑·실패 건수가 구조화 로그로 남는다 (event_id 추적 가능)

### FR-5. 스레드 묶음 — P0
키 `(channel_id, source, routing_key)`, 슬라이딩 120초(마지막 이벤트 create_date 기준 연장), 캡 30분/reply 200건.
- [ ] 같은 호스트의 120초 내 후속 critical/fatal은 루트 post의 reply로 부착된다
- [ ] 시간 판정은 이벤트 create_date끼리 비교하며 서버 시계와 혼용하지 않는다
- [ ] reply 포맷 = 루트 포맷에서 헤더 라인만 제거(심각도 뱃지 유지, 03 §5)
- [ ] HA: 두 노드가 동시에 첫 알람을 받아도 루트 post는 1개만 생성된다 (KV set-if-absent 선점)
- [ ] 캡 도달 시 새 루트를 시작한다

### FR-6. Jira 티켓 생성 — P0
채널 옵트인(jira.enabled), 우선 IT부문. ScriptRunner endpoint POST, PAT Bearer 인증.
- [ ] 스레드 루트 생성 시점에만 티켓 1건 생성, 티켓 링크를 스레드 reply로 게시
- [ ] MM 발송 완료 후 비동기 실행, 실패 시 재시도 1회 후 감사 채널 알림 — 알람 발송을 지연·차단하지 않는다
- [ ] project_key·issue_type을 요청 파라미터로 전송 (채널 설정값)
- [ ] Jira 미응답 상태에서도 알람 발송은 정상 동작한다

### FR-7. 관리 웹뷰 — P0
`/plugins/dmove-sycros/admin`, System Admin 전용. 4탭: 매핑 규칙 / 채널 관리 / 설정 / 상태·테스트 (목업 v2 기준).
- [ ] 규칙·채널 CRUD, 검색·소스 필터, JSON import/export
- [ ] 설정 탭에서 Jira endpoint URL·PAT 입력 — 별도 KV(integration:jira) 저장, **export에 미포함**, 화면엔 마지막 4자리만 표시, 연결 테스트 버튼
- [ ] 설정 탭에서 스레드 윈도우·캡·최소 심각도·동시 발송 수 조정
- [ ] 라우팅 테스트: source+key 입력 → 매칭 채널·Jira 생성 여부 미리보기(dry-run) 및 실발송
- [ ] 모든 쓰기는 감사 채널에 변경자·내용 요약 post, 버전 충돌(동시 편집) 시 409 + 재로드 안내
- [ ] 비관리자 접근 시 403. 기존 System Console 설정 UI는 무변경

### FR-8. 관측성 — P1
- [ ] 상태 API: 폴링 상태·마지막 tick·캐시 버전·당일 발송/미매핑/실패/Jira 카운트
- [ ] 일 1회 heartbeat 셀프테스트 알람 (리더 선출로 단일 발화)

### FR-9. 위생 정리 — P1
- [ ] 하드코딩된 Crowd DB 더미 접속정보의 config 주입 구조 전환, password_hint 로그 제거
- [ ] SQL 식별자(테이블/컬럼명) quoting 또는 화이트리스트 검증

**P2 (Future)**: 팀별 셀프서비스 권한, Jira 코멘트 미러링·회복 시 자동 종결, 스레드 키 세분화(event_id 조합), 채널별 severity 조절, 폭주 시 채널당 collapse, 담당자 찾기.

## 6. 비기능 요구사항

- **HA**: 2노드 동시 실행 전제. 공유 상태 선점은 KV atomic set-if-absent + TTL, 캐시는 TTL 수렴, 주기 작업은 리더 선출. 판단 불가 상황은 유실보다 중복(fail-open) + 로그
- **성능**: Sycros 원천 일 최대 1만(피크 분당 1,000, critical 이상은 저빈도) / Tmax 일 1,000건 이내. 발송은 bounded 동시성(기본 16)
- **폐쇄망**: 신규 외부 의존성 금지, 현 go.mod 범위 내 구현. 빌드 산출물 사내 반입 절차 준수
- **보안**: ingest 토큰 인증, PAT는 관리화면 입력·KV 분리 저장·export 제외, 값 파라미터 바인딩
- **호환**: plugin id `dmove-sycros` 불변. 기존 설정(notification_channels)·KV 키 보존

## 7. 성공 지표

- 선행: 미매핑 비율 — 도입 4주 후 주간 발송의 5% 이하 (fallback 채널 트리아지로 수렴) / 라우팅 발송 실패 0건 / Jira 생성 성공률 99%+ / 폭풍 시 채널 post 수: 스레드 도입 전 대비 80%+ 감소 (dlpap02 유형 사례 기준)
- 후행: 조직 채널 등록 수 확대 추이 / 채널 뮤트·이탈 없음 / Slack 전환 시 매핑 데이터 재사용 (조직-자원 매핑 자산화)
